# ЛР 2 — обоснование актуальности ВКР

**Тема ВКР:** Проектирование и разработка системы управления серверной инфраструктурой на основе декларативного описания ресурсов и базы данных управления конфигурациями

**Автор:** Игорь Яковлев ([@Golovastik777](https://github.com/Golovastik777)).

**Вклад участников:** работа индивидуальная.

## 0. Объект, проблема и масштаб работы

### Объект

Платформа «Почини.Онлайн» работает на шести виртуальных серверах у хостинг-провайдера VDSina: кластер k3s из трёх узлов, сервер резервного копирования, сервер мониторинга и тестовая среда. Отдельно работает сервер GitLab. Настройку ОС, сети, VPN и кластера выполняет Ansible (около 20 плейбуков и 25 ролей). Приложения в кластере разворачиваются через GitOps (Flux). Нижний слой при этом управляется вручную:

- серверы и локальная сеть создаются **вручную в панели хостинга**, затем данные о них вручную переносятся в инвентарь Ansible. Инструкция ввода рабочего узла содержит 12 шагов, часть из них выполняется в веб-панели;
- **единого источника данных нет**: внутренние адреса узлов вписаны руками в 149 строк конфигурации в нескольких репозиториях (334 вхождения с учётом тестовой сети). Роли хостов, VPN-пиры и правила межсетевого экрана заданы отдельными списками в YAML;
- **нет учёта** конфигурационных единиц и **контроля расхождений** между описанием и реальной инфраструктурой. Декларативное описание ресурсов (Terraform/OpenTofu) и база данных управления конфигурациями (далее — CMDB) в компании не используются.

Работа связывает эти слои в одну систему. CMDB (NetBox) хранит данные о конфигурации. Terraform создаёт ресурсы и записывает их в CMDB. Ansible берёт список узлов из CMDB. GitLab CI проверяет изменения до применения и по расписанию ищет расхождения.

### Масштаб: что будет описано декларативно

Оценка по репозиториям инфраструктуры (состояние на 31.10.2026) и API GitLab (07.11.2026):

| Система | Что описывается | Объём | Провайдер Terraform |
|---|---|---|---|
| VDSina | серверы, локальные адреса, SSH-ключи, расписания резервного копирования | 6 серверов, ≈ 20 объектов | открытый провайдер VDSina, дорабатывается в работе |
| NetBox (CMDB) | виртуальные машины, интерфейсы, адреса и префиксы трёх сетей, роли, сервисы, VPN-пиры | 7 машин, ≈ 90 объектов | `e-breuninger/netbox` |
| GitLab | группы, проекты, защищённые ветки, переменные CI, агент Kubernetes | 5 групп, 22 проекта, ≈ 100 объектов | `gitlabhq/gitlab` |
| Grafana | папки, дашборды, правила оповещений, точки контакта | 4 дашборда, 25 правил, ≈ 35 объектов | `grafana/grafana` |

Итого около **280 объектов в шести системах**. Ресурсы Kubernetes в Terraform не переносятся: ими уже управляет Flux.

### Окружения и организация конфигураций

Конфигурации организуются иерархически с помощью Terragrunt [23]. Каждая система — отдельный стек со своим состоянием в GitLab. Зависимости между стеками заданы явно: ключи и сеть → серверы → записи в NetBox → GitLab, Grafana, MinIO и DNS. Общие параметры задаются один раз и наследуются окружениями.

| Окружение | Серверов | Стеки | Жизненный цикл |
|---|---|---|---|
| Рабочее (prod) | 5 | все семь | постоянное; `apply` вручную после проверки `plan` |
| Тестовое (stage) | 1 | серверы, NetBox, DNS | постоянное |
| Временное для запроса на слияние | 1 | серверы, NetBox, DNS | создаётся при открытии запроса на слияние, удаляется при закрытии |

Тарифы VDSina в API указаны посуточно [25], поэтому короткоживущие окружения обходятся дёшево.

### Что создаётся в работе

1. **Доработка открытого Terraform-провайдера VDSina** [26]. Готовые провайдеры не управляют локальной сетью, хотя по ней работают etcd, Flannel и Longhorn. Также в них нет дополнительных IP-адресов и расписаний резервного копирования, а тестов почти нет (раздел 3, таблица 2). В работе добавляются три ресурса и приёмочные тесты на имитации API [24], проверяется импорт существующих серверов без пересоздания. Изменения передаются в исходный проект.
2. **Иерархия конфигураций Terragrunt** для трёх типов окружений с графом зависимостей стеков и отдельным состоянием на стек.
3. **Модель данных CMDB и связка NetBox ↔ Terraform ↔ Ansible.** Terraform записывает созданные ресурсы в NetBox, Ansible получает инвентарь из NetBox вместо статического `hosts.yml`.
4. **Конвейер GitLab CI.** Для каждого запроса на слияние выполняется `plan` всех затронутых стеков, `apply` запускается вручную. Временные окружения создаются и удаляются автоматически, проверка дрейфа выполняется по расписанию.

### Выводы по обзору

1. **Подходы, которые можно использовать.** Связка «декларативное описание ресурсов (Terraform/OpenTofu) + управление конфигурацией узлов (Ansible)» устоялась и в научных работах, и на практике [1–3; 8–10; 20]. Для нескольких окружений применяют иерархию конфигураций с явными зависимостями между стеками [2; 23]. Учёт конфигурационных единиц и контроль изменений требуют стандарты [4; 5], архитектура CMDB со сверкой данных из нескольких источников описана давно [7; 19]. NetBox как источник данных для Ansible выбран и в работах ИТМО [21], и в промышленности [22].
2. **Что уже сделано.** Систематизированы дефекты, антипаттерны и «запахи безопасности» [11–15], есть открытые датасеты кода Terraform и Ansible [17; 18]. Появились методы автоматического обнаружения и устранения дрейфа, но для крупных облаков с журналами API [16]. Для VDSina есть открытый провайдер [26], но он покрывает не все нужные операции API [25].
3. **Что остаётся нерешённым.** Декларативное описание и CMDB рассматриваются раздельно. В одних работах данные о конфигурации живут в коде и состоянии Terraform [8; 11–16; 20], в работах по CMDB нет связи с декларативным описанием [7; 19]. Российские работы по NetBox и Ansible [21] не охватывают создание ресурсов кодом и контроль расхождений. Небольшие инфраструктуры на VPS без зрелого провайдера и без журналов облачных API в рассмотренных работах не изучены.

## 3. Обзор и сравнение аналогов

### Прямые аналоги

Решают ту же задачу: единый источник данных об инфраструктуре, связанный с автоматизацией.

1. **NetBox Labs: NetBox + Discovery + Assurance** ([документация](https://netboxlabs.com/docs/assurance/)). NetBox хранит намеренное состояние: устройства, адреса, префиксы, виртуальные машины. Discovery собирает фактическое состояние, Assurance непрерывно сравнивает его с NetBox и показывает расхождения. Ограничения: Discovery и Assurance — платные дополнения к подписке NetBox Enterprise или Cloud; ориентированы на сетевое оборудование; ресурсы у хостинг-провайдера не создают.
2. **Nautobot + Single Source of Truth** (Network to Code, [документация](https://docs.nautobot.com/projects/ssot/en/latest/)). Форк NetBox с фреймворком задач и приложением синхронизации на библиотеке DiffSync (ServiceNow, Device42, Infoblox, vSphere и др.). Есть Terraform-провайдер (7 ресурсов, 14 источников данных). Ограничения: сетевой фокус; интеграцию с хостингом нужно писать самому; поиск расхождений для серверной инфраструктуры в базовой поставке не найден.
3. **ServiceNow CMDB + Service Graph Connector for Terraform** ([документация HashiCorp](https://developer.hashicorp.com/terraform/cloud-docs/integrations/service-now/service-graph)). Импортирует ресурсы из состояния Terraform в CMDB по расписанию или по уведомлению. Ограничения: нужны HCP Terraform или Terraform Enterprise и лицензия ITOM Discovery; готовые сопоставления только для AWS, Azure, GCP и vSphere; связь односторонняя (CMDB — копия состояния); вендор ушёл с российского рынка.

### Косвенные аналоги

Решают часть задачи или решают её другим способом.

1. **HCP Terraform** ([проверка состояния](https://developer.hashicorp.com/terraform/cloud-docs/workspaces/health)). Хранение состояния, запуск `plan`/`apply`, проверка дрейфа примерно раз в сутки. Ограничения: состояние Terraform — не CMDB (нет ролей, владельцев, сервисов, связей); проверка дрейфа только в платных редакциях Standard и Premium; Terraform с 2023 г. под лицензией BSL; реестр провайдеров недоступен с российских IP-адресов.
2. **Российские ITSM-платформы с CMDB (SimpleOne, Naumen Service Desk)** — замена ServiceNow после 2022 г. Ограничения: CMDB обслуживает процессы поддержки (инциденты, изменения); готовой связки с Terraform и динамическим инвентарём Ansible в открытой документации не найдено; платные лицензии.
3. **Terraform + Ansible без CMDB** (например, система Челноковой А. В. [20]). Создание ресурсов и настройка автоматизированы, но данные о конфигурации остаются в файлах и состоянии Terraform; учёта нет.
4. **Текущий процесс «Почини.Онлайн»: панель хостинга + статический инвентарь Ansible.** Ручное создание серверов, адреса продублированы, расхождения не отслеживаются (раздел 0).

### Выводы по сравнению

1. Ни одно решение не закрывает задачу целиком: лучшие аналоги выполняют 5 и 4 критерия из 8. CMDB-платформы хранят данные, но не создают ресурсы у хостинга. HCP Terraform создаёт ресурсы и ищет дрейф, но не ведёт учёт. В ServiceNow связь односторонняя.
2. Обнаружение расхождений в готовых продуктах платное (NetBox Assurance, HCP Terraform Standard/Premium, ServiceNow ITOM) и рассчитано на сетевое оборудование или крупные облака.
3. Открытый провайдер VDSina существует, но не управляет локальной сетью, дополнительными адресами и расписаниями резервного копирования и почти не покрыт тестами. Без локальной сети инфраструктуру «Почини.Онлайн» описать нельзя: по ней работают etcd, Flannel и Longhorn. Поэтому провайдер дорабатывается, а не пишется заново.
4. **Что берём из существующих решений:** NetBox как CMDB и его экосистему (провайдер `e-breuninger/netbox`, коллекция Ansible `netbox.netbox`); идею «намеренное состояние ↔ факт» из NetBox Assurance; плановую проверку дрейфа из HCP Terraform (через `plan` по расписанию в GitLab CI); открытый провайдер VDSina как основу; провайдер `sport24ru/regru` для записей DNS; Terragrunt для окружений.
5. **Какие ограничения устраняем:** односторонность связи CMDB и декларативного описания; неполноту провайдера VDSina; платность проверки дрейфа; ручное дублирование адресов в инвентаре.

## 4. Итоги

**Итоговая тема ВКР:** Проектирование и разработка системы управления серверной инфраструктурой на основе декларативного описания ресурсов и базы данных управления конфигурациями

**УДК для тезиса:** 004.42 — так же, как в близкой по теме работе об автоматизированном развёртывании инфраструктуры на Terraform и Ansible [20].

**Ключевые слова:** декларативное описание инфраструктуры, база данных управления конфигурациями, единый источник данных, управление конфигурацией, дрейф конфигурации, NetBox, Terraform, OpenTofu, Terragrunt, Ansible.

### Актуальность исследования

1. **Ручное управление порождает ошибки и расхождения.** Декларативное описание сокращает ручные операции [3; 20], но и само содержит дефекты и уязвимости, а в промышленности остаются проблемы поддержки и согласованности [11–14]. В объекте исследования серверы создаются вручную, адреса продублированы в 149 строках конфигурации. При изменении адреса или роли узла приходится вручную править несколько репозиториев.
2. **Расхождение «описание ↔ реальность» признано отраслевой проблемой.** В 2024–2025 гг. NetBox Labs выпустила отдельный продукт для поиска расхождений с CMDB (NetBox Assurance), а HashiCorp включила проверку дрейфа в платные редакции HCP Terraform. Автоматическое устранение дрейфа изучают и в науке [16]. Управление конфигурацией и учёт конфигурационных единиц требуют стандарты [4; 5].
3. **Изменились условия рынка в 2022–2025 гг.** ServiceNow ушёл с российского рынка, реестр провайдеров Terraform недоступен с российских IP-адресов, Terraform перешёл на лицензию BSL (2023), появился открытый форк OpenTofu, HashiCorp вошла в состав IBM (2025). Небольшим российским командам нужен стек на открытых компонентах, который работает на собственных серверах.
4. **Пробел в существующих решениях.** Готовые продукты рассчитаны на сетевое оборудование и крупные облака (таблица 1), а открытый провайдер российского хостинга покрывает API не полностью (таблица 2). Схема, в которой CMDB служит входом для Terraform и Ansible, окружения организованы иерархически, а расхождения проверяются автоматически, для инфраструктуры на VPS в рассмотренных источниках [7; 11–22] и аналогах не описана. Это и составляет новизну работы.

### Цель исследования

Повысить воспроизводимость и управляемость серверной инфраструктуры платформы «Почини.Онлайн». Для этого разрабатывается система, в которой CMDB служит единым источником данных о конфигурации для Terraform/OpenTofu и Ansible, а окружения описаны иерархически. В результате должно сократиться число ручных операций при вводе узлов и создании окружений, а расхождения описания с реальной инфраструктурой должны обнаруживаться автоматически.

### Задачи исследования

1. Проанализировать текущую инфраструктуру и процессы управления, зафиксировать базовые метрики (таблица 4).
2. Сравнить существующие провайдеры VDSina и REG.RU и способы организации конфигураций для нескольких окружений; обосновать выбор.
3. Разработать модель данных CMDB: конфигурационные единицы (виртуальные машины, интерфейсы, адреса и префиксы трёх сетей, роли, сервисы, VPN-пиры, владельцы) и связи между ними.
